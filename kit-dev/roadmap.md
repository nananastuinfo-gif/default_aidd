# Default AIDD ロードマップ

このリポジトリは「AIDD の進め方キット」の開発用リポジトリです。新しいプロジェクトは、
ここからリリースした配布用のテンプレートリポジトリを雛形として開始します。進め方の原則は [憲章](../.specify/memory/constitution.md) を参照してください。

> このファイルは雛形の開発専用です(`kit-dev/` 配下)。リリース時に除外され、配布用リポジトリには含まれません。

最終更新: 2026-11-03(フェーズ 2 の説明を追加)

## 前提(2026-11-01 時点の合意)

| 項目 | 決定内容 |
|------|----------|
| 利用形態 | 新規プロジェクトは配布用リポジトリから GitHub の「Use this template」で開始する |
| 利用者 | 当面は個人。将来に備え GitHub Issue 駆動 + PR で進める |
| 開発用リポジトリ | https://github.com/nananastuinfo-gif/default_aidd (public、Template repository 無効)。Issue・PR はここに集める |
| 配布用リポジトリ | 名前は `aidd-template`。フェーズ 4 で作成する。`kit-dev/` を除いた確定版を反映し、タグで版を管理する。Template repository を有効にする |
| ブランチ保護 | `main` は PR 必須(承認数 0、管理者にも適用)、force push・削除は禁止 |
| 雛形の開発専用ファイル | `kit-dev/` に集約し、リリース時に除外する |
| AI エージェント | Claude Code のみ。他エージェント導入時は、対応を追加するか別標準を作成する |
| 試行テーマ | Teamfight Tactics(TFT)の日本コミュニティ活性化。アイデア出し → 調査 → 開発の全工程を試す |

## フェーズ

| # | 内容 | 状態 |
|---|------|------|
| 0 | 憲章 v1.0.0 の制定・初回コミット | 完了 |
| 1 | 改善ループ(改善提案の収集 → 振り返り → 改定までの手順と仕組み) | 完了(#3、手順書: `docs/improvement-loop.md`) |
| 2 | 原則を守るための自動チェック(`CLAUDE.md`、hooks)。改善提案 #8(作業ブランチの自動作成)を含む | 次に着手 |
| 3 | 種別ごとのテンプレート(アイデア出し・調査/検証・報告資料、ADR) | 未着手 |
| 4 | 配布用リポジトリとリリース手順(`kit-dev/` を除外して反映・タグ付け)、派生先での標準更新の取り込み | 未着手 |
| 5 | 試行: TFT プロジェクトを雛形から作成し、全工程を実施 | 未着手 |

- フェーズ 1〜4 は、それぞれ Spec Kit の流れ(`/speckit-specify` → `/speckit-clarify` →
  `/speckit-plan` → `/speckit-tasks` → `/speckit-implement`)で進める。
- フェーズ 5 は 4 の最初のリリース後に、配布用リポジトリから派生して開始する。
  試行中の気づきは、フェーズ 1 の改善ループを通してこのリポジトリに還元する。

## 各フェーズの進め方

1. GitHub Issue を作成する(フェーズ 1 の完了までは手動)。
2. Issue に対応するブランチで `/speckit-specify` を実行し、以降のコマンドを順に進める。
3. PR を作成し、レビュー・承認を経てマージする。
4. 振り返りを PR に記録し(`docs/improvement-loop.md`)、このロードマップの状態を更新する。

## 雛形コピー方式の注意点と対策

| 注意点 | 対策 |
|--------|------|
| 単純なコピーでは雛形の Git 履歴まで引き継がれる | 配布用リポジトリの「Use this template」から作成する(履歴なしで開始できる) |
| 雛形を改善しても、作成済みのプロジェクトには反映されない | リリースのタグを基準に差分を取り込む手順をフェーズ 4 で整備する(Spec Kit の preset 化も検討) |
| 派生プロジェクトでの改善点が雛形に戻らない | フェーズ 1 で、派生プロジェクトから開発用リポジトリに改善提案の Issue を出す経路を定める |
| 雛形固有のファイル(このロードマップ等)が派生先に残る | 開発用と配布用でリポジトリを分け、リリース時に `kit-dev/` を除外する(派生先での削除作業は不要) |
| 派生先で改善ループのラベルがなく、Issue フォームのラベルが付かない | 派生時の手順に、Issue フォームの表示確認と `scripts/setup-labels.sh` の実行を含める(フェーズ 4) |

## フェーズ 1: `/speckit-specify` に渡す説明

```text
AIDD 標準プロセスを使う中で得た気づきを、継続的に標準(憲章・テンプレート・手順)へ反映する
「改善ループ」を整備する。

背景:
- 憲章 v1.0.0 は Governance で改定手続き(提案 → 承認 → バージョン更新)を定めているが、
  日々の気づきを収集し、改定提案にまとめるまでの具体的な仕組みがない。
- 運用は個人だが、GitHub Issue 駆動 + PR で進める。AI エージェントは Claude Code のみを使う。
- このリポジトリは新規プロジェクトの雛形として使われるため、派生プロジェクトで得た気づきも
  雛形に還元できる必要がある。

実現したいこと:
1. 改善提案の記録: 作業中に気づいた問題・改善案を、手間なく GitHub Issue として登録できる
   (専用の Issue テンプレートとラベル。対象が憲章・テンプレート・手順のどれかを区別できる)。
2. 振り返り: 各タスク(PR)の完了時に、所定の観点(うまくいった点・問題点・改善提案)で
   振り返りを行い、改善提案は 1 の Issue に変換される。
3. 改定の判断: 溜まった改善提案を定期的に(または随時)見直し、
   「憲章の改定(/speckit-constitution)」「テンプレート・手順の修正」「見送り」に振り分ける
   手順がある。判断結果と理由は Issue に記録される。
4. 反映: 改定は通常の Issue → ブランチ → PR の流れで行い、憲章の改定ではバージョンが更新される。
5. 派生プロジェクトからの還元: 配布用リポジトリ(aidd-template)から派生したプロジェクトで得た改善提案を、
   開発用リポジトリ(default_aidd)の Issue として
   登録する手順がある。

成功基準:
- 改善提案の登録から改定の反映まで、手順書だけを見て一人で実施できる。
- 改善提案 1 件を、登録から PR マージまで実際に一巡できる(このフェーズ自体の振り返りで検証する)。
- すべての改善提案について、採否と理由を後から追跡できる。

対象外:
- 原則を守るための自動チェック(hooks 等)。フェーズ 2 で扱う。
- 配布用リポジトリへのリリースと、派生プロジェクトへの標準更新の配布。フェーズ 4 で扱う。
```

## フェーズ 2: `/speckit-specify` に渡す説明

```text
AIDD 標準プロセスの原則のうち、機械的に判定できるものを Claude Code の hooks・設定で自動チェックし、
日常的な実行時ガイダンスを CLAUDE.md に整備する。

背景:
- 憲章 v1.1.0 は MUST/MUST NOT を定めているが、守れているかは人間と AI の注意力に頼っている。
- フェーズ 1 の振り返りで、Spec Kit の git 拡張が未導入のため、specify 時の作業ブランチ作成が
  手動になっており、忘れやすく、命名もその場で決めていたことが分かった(改善提案 #8、
  判断「テンプレート・手順の修正」、反映先はフェーズ 2)。
- CLAUDE.md は「全体の整備はフェーズ 2 で行う」とした暫定版のままになっている。
- 運用は個人で、AI エージェントは Claude Code のみを使う。このリポジトリは雛形として配布されるため、
  チェックの仕組みは派生プロジェクトでもそのまま動く必要がある。

実現したいこと:
1. 作業ブランチ(#8 の対応): /speckit-specify の開始時に、Issue 番号と対応づいた命名規則で
   作業ブランチが自動で作成される(または、作成されていなければ先に進まない)。
   命名規則は手順書に明記する。git 拡張を導入するか、独自の hook で実装するかは調査して決める。
2. 既定ブランチの保護: 既定ブランチ(main)上でのコミットを hook で止め、作業ブランチの作り方を案内する。
3. 取り消しが困難な操作の確認: force push、ブランチの削除、PR のマージ、ファイルの一括削除などは、
   実行前に必ず人間の確認を求める(Claude Code の permissions 設定で実現する)。
4. 機密情報の混入防止: 認証情報らしい文字列(API キー、トークン、秘密鍵など)を含むコミットを止める。
5. 仕様ゲートの確認: 未解決の [NEEDS CLARIFICATION] が spec に残っている状態で
   /speckit-plan に進もうとしたら警告する。
6. CLAUDE.md の整備: 憲章の原則を日々の作業手順に落とし込んだガイドと、上記チェックの一覧
   (何を、なぜ、止められたときの対処)を記載する。憲章と矛盾してはならない。

制約:
- チェックで止めるときは、理由と対処方法をメッセージに示す。
- 誤検知などで正当にチェックを外す場合は、その理由を記録する(憲章 Governance の
  「逸脱は理由を記録した場合に限り許容」に合わせる)。
- 実行環境の前提は git・bash・python3 のみとし、追加の依存を増やさない。
- 設定とスクリプトはリポジトリにコミットし、派生プロジェクトに追加作業なしで引き継がれる。

成功基準:
- 実現したいこと 1〜5 の各チェックについて、「止まる(または警告する)ケース」と
  「止まらないケース」をそれぞれ 1 件以上実際に再現し、結果を記録している。
- main 上で Claude Code にコミットさせようとすると、コミットが作成されない。
- /speckit-specify を main 上で開始すると、命名規則どおりの作業ブランチが作成されている。
- CLAUDE.md だけを読めば、各チェックの内容と止められたときの対処が分かる。
- 改善提案 #8 が、このフェーズの PR マージで改善ループの手順どおりに完了している。

対象外:
- プロジェクト固有のテスト・静的解析の実行(品質ゲート 3)。派生プロジェクトごとに定める。
- GitHub Actions などの CI によるチェック(PR の振り返り欄の記入確認など)。
- 種別ごとのテンプレート(フェーズ 3)、配布用リポジトリへのリリース(フェーズ 4)。
```
