# Feature Specification: 改善ループの整備

**Feature Branch**: `001-improvement-loop`

**Created**: 2026-11-01

**Status**: Approved (2026-11-01)

**Input**: User description: "AIDD 標準プロセスを使う中で得た気づきを、継続的に標準(憲章・テンプレート・手順)へ反映する「改善ループ」を整備する。(GitHub Issue #3)"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 改善提案を手間なく登録する (Priority: P1)

運用者(当面は個人)が、AIDD 標準プロセスに沿って作業している最中に、憲章・テンプレート・手順の
問題や改善案に気づく。作業の流れを止めずに、所定の書式で改善提案を GitHub Issue として登録し、
後で判断できる状態にしておく。

**Why this priority**: 気づきを記録する受け皿がなければ、以降の判断・反映はすべて成り立たない。
これだけでも「気づきが流れて消える」という最大の問題を解消できる。

**Independent Test**: 架空の気づき 1 件を、手順書だけを見て改善提案として登録し、
対象区分・発生状況・問題点・改善案が揃った状態で、提案の一覧に表示されることを確認する。

**Acceptance Scenarios**:

1. **Given** 運用者が作業中に手順の不備に気づいた, **When** 改善提案の書式を使って登録する,
   **Then** 対象区分(憲章/テンプレート/手順)・発生状況・問題点・改善案を含む提案が
   「未判断」の状態で登録される
2. **Given** 改善提案が複数登録されている, **When** 運用者が提案の一覧を見る,
   **Then** 改善提案だけを他の Issue と区別して一覧でき、対象区分と状態で絞り込める
3. **Given** Claude Code が作業中に標準の改善点に気づいた, **When** Claude Code が提案の登録を
   申し出る, **Then** 運用者が内容を確認・承認してから登録される

---

### User Story 2 - 改善提案を判断し、標準に反映する (Priority: P2)

運用者が、溜まった改善提案を見直し、各提案を「憲章の改定」「テンプレート・手順の修正」
「見送り」のいずれかに振り分け、判断理由を記録する。採用した提案は通常の
Issue → ブランチ → PR の流れで反映し、反映されたことが提案から辿れる。

**Why this priority**: 提案を登録するだけでは標準は改善されない。判断と反映が揃って初めて
ループが一巡し、成功基準「登録から PR マージまで一巡できる」を満たせる。

**Independent Test**: User Story 1 で登録した提案 1 件について、手順書だけを見て判断・理由の記録・
反映 PR のマージまで行い、提案から判断理由と反映 PR に辿れることを確認する。

**Acceptance Scenarios**:

1. **Given** 未判断の改善提案がある, **When** 運用者が見直しを行う, **Then** 提案は 3 区分の
   いずれかに振り分けられ、判断理由が提案に記録される
2. **Given** 「テンプレート・手順の修正」と判断された提案がある, **When** 修正の PR がマージされる,
   **Then** 提案は「反映済み」となり、提案から反映 PR を辿れる
3. **Given** 「憲章の改定」と判断された提案がある, **When** 改定を行う, **Then** 憲章の改定手続きに
   従ってバージョンが更新され、改定内容と提案が相互に辿れる
4. **Given** 「見送り」と判断された提案がある, **When** 判断を記録する, **Then** 理由とともに
   提案が閉じられ、後から同種の提案が出たときに過去の判断を参照できる

---

### User Story 3 - PR の完了時に振り返り、改善提案につなげる (Priority: P3)

運用者が、各タスクの PR を完了するときに、所定の観点(うまくいった点・問題点・改善提案)で
振り返りを記録する。振り返りで出た改善提案は、User Story 1 の改善提案として登録される。

**Why this priority**: 作業中の気づき(User Story 1)だけでは拾いきれない学びを、決まった
タイミングで定期的に拾い上げる仕組みになる。ただし、登録と判断の受け皿が先に必要なため P3 とする。

**Independent Test**: 任意の PR 1 件について振り返りを記録し、改善提案があればその提案 Issue への
参照が振り返りに含まれていることを確認する。

**Acceptance Scenarios**:

1. **Given** PR を作成する, **When** 運用者が PR の説明を記入する, **Then** 振り返りの 3 観点を
   記入する欄が用意されている
2. **Given** 振り返りで改善提案が出た, **When** PR をマージする前に, **Then** その改善提案が
   改善提案として登録され、振り返りから参照されている
3. **Given** 小さな変更で特に振り返る内容がない, **When** 振り返りを記入する, **Then** 「特になし」と
   記入することで完了できる

---

### User Story 4 - 派生プロジェクトから改善提案を還元する (Priority: P4)

配布用リポジトリ(aidd-template)から派生したプロジェクトの運用者が、標準そのものに関わる
気づきを、開発用リポジトリ(default_aidd)の改善提案として登録する。

**Why this priority**: 派生プロジェクトはフェーズ 5 まで存在しないため、優先度は最も低い。
ただし、派生先に配布される手順書に経路が書かれていないと、後から還元されなくなるため本フェーズで定める。

**Independent Test**: 派生プロジェクトに配布される手順書だけを見て、開発用リポジトリに
出典(派生プロジェクト名)付きの改善提案を登録できることを確認する。

**Acceptance Scenarios**:

1. **Given** 派生プロジェクトで標準の不備に気づいた, **When** 配布された手順書に従う,
   **Then** 開発用リポジトリに、出典となる派生プロジェクト名を含む改善提案が登録される
2. **Given** 派生プロジェクト固有の問題に気づいた, **When** 手順書を確認する, **Then** それは
   開発用リポジトリへの還元対象ではなく、派生プロジェクト内で扱うものだと判別できる

---

### Edge Cases

- 同じ内容の改善提案が重複して登録された場合、一方に統合し、相互に参照したうえで重複側を閉じる。
- 1 件の提案が複数の対象区分(例: 憲章とテンプレート)にまたがる場合、主な対象区分を 1 つ選び、
  判断時に必要なら提案を分割する。
- 過去に見送った内容と同種の提案が再び登録された場合、過去の判断を参照し、前提が変わったかを
  判断理由に記録する。
- 判断のために追加情報が必要な場合、提案を「未判断」のまま追加情報の依頼を記録し、
  判断を保留できる。
- 反映 PR がマージされずに中止された場合、提案は「反映済み」にならず、判断の見直し対象に戻る。
- 憲章の改定が後方互換性のない変更(MAJOR)になる場合も、通常の改定手続きと同じく
  運用者の承認を経てから反映する。
- 派生プロジェクトからの提案に、判断に必要な文脈(発生状況など)が欠けている場合、
  追加情報の依頼として扱う。

## Requirements *(mandatory)*

### Functional Requirements

**改善提案の登録**

- **FR-001**: 運用者は、所定の書式で改善提案を GitHub Issue として登録できなければならない。
  書式の必須項目は、対象区分・発生状況(どの作業で気づいたか)・問題点・改善案・出典
  (このリポジトリか、派生プロジェクト名か)とする。
- **FR-002**: 対象区分は「憲章」「テンプレート」「手順」のいずれかを選べなければならない。
- **FR-003**: 改善提案は、他の Issue と区別して一覧でき、対象区分と状態で絞り込めなければならない。
- **FR-004**: 改善提案の状態として、少なくとも「未判断」「対応予定(憲章の改定)」
  「対応予定(テンプレート・手順の修正)」「見送り」「反映済み」を識別できなければならない。
- **FR-005**: Claude Code が改善提案を登録する場合、登録前に運用者の確認と承認を得なければならない
  (憲章 VI)。

**改定の判断**

- **FR-006**: 運用者は、未判断の改善提案を「憲章の改定」「テンプレート・手順の修正」「見送り」の
  いずれかに振り分け、判断理由を当該提案に記録できなければならない。
- **FR-007**: 見直しは随時行えるほか、少なくとも各フェーズ(各機能)の完了時と、憲章が定める
  四半期ごとの見直しの際に、未判断の提案をすべて確認しなければならない。
- **FR-008**: 「見送り」と判断した提案は、理由を記録したうえで閉じられ、後から検索・参照できなければ
  ならない。
- **FR-009**: 重複した提案は、統合先を記録したうえで閉じられなければならない。

**反映**

- **FR-010**: 採用した提案の反映は、Issue → ブランチ → PR の流れで行い、反映 PR は対象の提案を
  参照しなければならない。
- **FR-011**: 反映 PR のマージによって、提案は「反映済み」となり閉じられなければならない。
- **FR-012**: 「憲章の改定」の反映は、憲章の Governance に定める改定手続き(`/speckit-constitution`
  による提案、運用者の承認、セマンティックバージョニングに従うバージョン更新)に従わなければならない。

**振り返り**

- **FR-013**: すべての PR に、振り返りの 3 観点(うまくいった点・問題点・改善提案)を記入する欄が
  用意されていなければならない。
- **FR-014**: 振り返りに改善提案がある場合、PR のマージ前にその提案を改善提案として登録し、
  振り返りから参照しなければならない。
- **FR-015**: 振り返る内容がない場合は「特になし」と記入して完了できなければならない。

**派生プロジェクトからの還元**

- **FR-016**: 派生プロジェクトの運用者が、開発用リポジトリに出典付きの改善提案を登録する手順が
  なければならない。
- **FR-017**: FR-016 の手順と、還元対象(標準そのものに関わるもの)と対象外(派生プロジェクト固有の
  もの)の判別基準は、配布用リポジトリに含まれる場所(`kit-dev/` の外)に置かれなければならない。

**手順書**

- **FR-018**: 登録・判断・反映・振り返り・還元の一連の手順は、1 つの手順書にまとめられ、
  手順書だけを見て運用者が一人で実施できなければならない。
- **FR-019**: 手順書は、憲章の Governance および「開発ワークフローと品質ゲート」と矛盾しては
  ならない。

### Key Entities

- **改善提案**: 標準(憲章・テンプレート・手順)への改善の申し出。対象区分・発生状況・問題点・
  改善案・出典・状態・判断結果・判断理由・反映 PR への参照を持つ。
- **振り返り**: PR に紐づく記録。うまくいった点・問題点・改善提案(改善提案への参照)を持つ。
- **判断記録**: 改善提案ごとの振り分け結果(3 区分)と理由。見送りや保留の理由も含む。
- **反映(改定)**: 採用された提案を標準に適用する PR。憲章の改定の場合は、改定前後のバージョンを持つ。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 運用者は、作業中の気づき 1 件を 3 分以内に改善提案として登録できる。
- **SC-002**: 運用者は、手順書以外の資料や他者の助けを借りずに、改善提案 1 件を登録から
  反映 PR のマージまで一巡できる(本フェーズの振り返りで実際に一巡して検証する)。
- **SC-003**: すべての改善提案(100%)について、判断結果と理由、および反映済みの場合は反映 PR を、
  提案から辿れる。
- **SC-004**: 未判断のまま 30 日を超えて放置される改善提案が 0 件である。
- **SC-005**: 本フェーズ完了後にマージされたすべての PR(100%)に、振り返りが記録されている。
- **SC-006**: 派生プロジェクトの運用者は、配布された手順書だけを見て、5 分以内に開発用リポジトリへ
  改善提案を登録できる。

## Assumptions

- GitHub Issue と PR を記録の場とすることは運用者の決定事項であり、実現手段の選択ではなく前提条件として
  扱う。
- 運用者は当面 1 人で、提案・判断・承認をすべて同じ人が行う。チーム運用での役割分担は対象外とする。
- 対象区分は当面「憲章」「テンプレート」「手順」の 3 つとする。フェーズ 2 以降で自動チェック等が
  加わった場合は、改善ループ自体で区分の追加を判断する。
- 振り返りはすべての PR を対象とするが、小さな変更では「特になし」を許容し、負担を抑える。
- 派生プロジェクト固有の改善は派生プロジェクト内で扱い、開発用リポジトリへは標準そのものに関わる
  提案だけを還元する。
- 開発用リポジトリは public であり、派生プロジェクトの運用者も改善提案を登録できる。
- 原則を守るための自動チェック(hooks 等)はフェーズ 2、配布用リポジトリへのリリースと派生先への
  標準更新の配布はフェーズ 4 で扱い、本フェーズの対象外とする。
