# Default AIDD Constitution

本憲章は、AI 駆動開発(AIDD)における今後すべてのプロジェクトの標準となる進め方を定める。
アイデア出し、調査・検証、システム開発、報告資料の作成のいずれのタスクにも共通して適用される。

## Core Principles

### I. 目的・成功基準の先行定義 (Spec-First)

- すべてのタスクは、着手前に「目的(解きたい課題・問い)」「スコープ(対象/対象外)」
  「成功基準(完了を判定できる条件)」を文書化しなければならない(MUST)。
- 成功基準は第三者が達成/未達を判定できる形で記述しなければならない(MUST)。
  「良い感じに」「なるべく」等の曖昧な表現は使用してはならない(MUST NOT)。
- 不明点は推測で埋めず、`[NEEDS CLARIFICATION]` として明示し、着手前に解消する(MUST)。

**理由**: 目的と完了条件が曖昧なままでは、AI・人間ともに作業の方向性と終了判断を誤る。

### II. タスク種別に応じたプロセス選択

- タスクは開始時に「アイデア出し」「調査・検証」「システム開発」「報告資料の作成」のいずれか
  (または組み合わせ)に分類し、本憲章「タスク種別ごとの標準プロセス」に定める手順と成果物に従わなければならない(MUST)。
- 種別をまたぐ場合(例: 調査結果を受けて開発へ移行、調査結果を報告資料にまとめる)、前段の成果物と結論を次段の入力として
  明示的に引き継がなければならない(MUST)。
- 定められたプロセスを省略・簡略化する場合は、その理由を成果物に記録する(MUST)。

**理由**: タスクの性質ごとに必要な厳密さと成果物は異なり、適切な型を選ぶことで過不足を防ぐ。

### III. 根拠に基づく判断と検証可能性 (Evidence-Based)

- 判断・主張には根拠(出典 URL、実測結果、ログ、コード参照など)を付さなければならない(MUST)。
- 記述は「事実」「推論」「仮定」を区別して示さなければならない(MUST)。
- 検証・実験は、前提条件・手順・環境・結果を記録し、第三者が再現できる状態にする(MUST)。
- 検証で否定された仮説や失敗した試行も、結論とともに記録する(MUST)。
- 報告資料に記載する数値・主張は、出典または元となる調査・検証の成果物を辿れるようにしなければ
  ならない(MUST)。

**理由**: AI の出力は誤りや幻覚を含み得るため、根拠と再現性がなければ信頼して意思決定できない。

### IV. 小さく段階的に進める (Incremental & Simple)

- 作業は独立して価値を確認できる最小単位(ユーザーストーリー、検証項目、アイデア候補)に分割し、
  優先度順に進めなければならない(MUST)。
- 現時点で必要とされない機能・抽象化・汎用化を追加してはならない(MUST NOT, YAGNI)。
- 複雑さを導入する場合は、より単純な代替案を検討した上で、その不採用理由を記録する(MUST)。

**理由**: 小さな単位で検証することで、手戻りコストを抑え、早期に方向修正できる。

### V. テストと品質ゲート (NON-NEGOTIABLE: システム開発)

- システム開発では、受け入れ基準に対応するテストを実装と同時またはそれ以前に作成し、
  テストが失敗することを確認してから実装する(MUST)。
- すべての変更は、テスト・静的解析(リンター/型チェック等、該当する場合)を通過しなければ
  マージしてはならない(MUST NOT)。
- 調査・検証で作成した PoC コードは、品質ゲートを通過しない限り本番コードとして
  流用してはならない(MUST NOT)。

**理由**: 自動テストは AI が生成したコードの正しさを継続的に保証する唯一のスケーラブルな手段である。

### VI. 人間による判断と承認 (Human-in-the-Loop)

- AI エージェントは提案・作成を担い、以下の節目では人間の承認を得なければならない(MUST):
  仕様(目的・成功基準)の確定、計画・設計の確定、マージ/リリース、方針の大きな変更。
- 取り消しが困難な操作(データ削除、本番環境への反映、外部への公開・送信)は、
  事前に人間の明示的な確認を得なければ実行してはならない(MUST NOT)。
- 機密情報(認証情報、個人情報、社外秘情報)を成果物・コミット・外部サービスに含めてはならない
  (MUST NOT)。

**理由**: 最終的な責任は人間が負うため、重要な意思決定と不可逆な操作は人間が統制する。

### VII. トレーサビリティと知識の蓄積

- 成果物(仕様・調査レポート・計画・タスク・決定記録)は Git でバージョン管理されたリポジトリに
  保存しなければならない(MUST)。
- 重要な意思決定は、背景・選択肢・決定・理由を決定記録(ADR 形式等)として残す(MUST)。
- コミットメッセージは変更の意図が分かる形式(Conventional Commits を推奨)で記述する(SHOULD)。
- タスク完了時は、得られた知見・課題・次のアクションを振り返りとして記録する(SHOULD)。

**理由**: 経緯と知見を蓄積することで、後続のタスクや他のメンバー・AI が文脈を再構築できる。

## タスク種別ごとの標準プロセス

| 種別 | 主な問い | 標準手順 | 必須成果物 | 完了条件 |
|------|----------|----------|------------|----------|
| アイデア出し | 何を作る/解くべきか | 課題定義 → 発散(複数案) → 評価軸の定義 → 収束・選定 | 課題定義、候補一覧、評価軸と評価結果、選定理由 | 次に進む候補と理由が承認されている |
| 調査・検証 | それは可能か/どれが最適か | 問い・仮説の設定 → 調査/検証計画 → 実施 → 結論 | 問いと仮説、調査方法、根拠付き結果、結論と推奨、未解決事項 | 問いに対する結論が根拠付きで示され承認されている |
| システム開発 | どう作り、正しく動くか | 仕様 → 明確化 → 計画 → タスク分解 → 実装 → 検証 | spec、plan、tasks、テスト、実装コード | 受け入れ基準を満たし品質ゲートを通過している |
| 報告資料の作成 | 誰に何を伝え、どう判断・行動してもらうか | 目的・読み手の定義 → 要点(結論)と構成の設計 → 根拠・素材の収集 → 作成 → レビュー・修正 → 提出 | 目的と読み手の定義、構成案(要点と章立て)、資料本体、根拠の出典一覧 | 読み手の判断・行動に必要な要点が根拠付きで資料に含まれ、提出前に承認されている |

- システム開発は Spec Kit のコマンド(`/speckit-specify` → `/speckit-clarify` → `/speckit-plan`
  → `/speckit-tasks` → `/speckit-analyze` → `/speckit-implement`)の流れに従う(MUST)。
- アイデア出し・調査・検証・報告資料の作成も同じ `specs/` 配下の機能ディレクトリ単位で成果物を管理し、
  上表の必須成果物を仕様・計画文書内に含める(MUST)。
- 想定期間・工数の上限(タイムボックス)を事前に設定し、超過する場合は継続可否を人間が判断する
  (SHOULD)。

## 開発ワークフローと品質ゲート

- **ブランチ運用**: 作業はタスク単位のブランチで行い、既定ブランチへ直接コミットしてはならない
  (MUST NOT)。
- **ゲート 1(仕様)**: 目的・スコープ・成功基準が記述され、未解決の `[NEEDS CLARIFICATION]`
  がないこと。
- **ゲート 2(計画)**: 計画が本憲章の各原則に適合していることを確認(Constitution Check)し、
  違反がある場合はその正当化が記録されていること。
- **ゲート 3(実装/結論)**: システム開発ではテスト・静的解析が通過していること。
  調査・検証では結論と根拠が記録されていること。
  報告資料の作成では、資料本体と根拠の出典一覧が揃い、記載内容が出典と一致していること。
- **ゲート 4(レビュー/マージ)**: 人間によるレビューと承認を経ていること。レビューでは本憲章への
  適合性を確認する。

## Governance

- 本憲章は、本プロジェクトおよび本プロジェクトを標準として利用するすべてのプロジェクトにおいて、
  他の慣行・個別ルールに優先する。
- **改定手続き**: 改定は `/speckit-constitution` により提案し、変更内容・理由・影響範囲
  (Sync Impact Report)を添えて人間の承認を得た上で反映する。
- **バージョニング**: セマンティックバージョニングに従う。
  - MAJOR: 原則の削除・再定義など後方互換性のない変更
  - MINOR: 原則・セクションの追加、または指針の実質的な拡充
  - PATCH: 文言の明確化、誤字修正など意味を変えない修正
- **遵守確認**: 計画作成時(Constitution Check)およびレビュー時に本憲章への適合を確認する。
  原則からの逸脱は、理由と代替案の検討結果を成果物に記録した場合に限り許容される。
- **定期見直し**: 本憲章は少なくとも四半期に一度、運用実績に基づき見直す(SHOULD)。
- 日常的な実行時ガイダンスは `CLAUDE.md` 等のエージェント向けガイドファイルに記述し、
  本憲章と矛盾してはならない(MUST NOT)。
